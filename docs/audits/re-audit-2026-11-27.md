## 1. Executive verdict

**NOT PRODUCTION READY. Do not use for live patient care, dispensing, immunization, laboratory reporting, insurance submission or financial processing.**

The repository is a meaningful development foundation, not a complete clinic operating system. It contains 22 registered FastAPI routers, a MongoDB persistence layer, OIDC RS256/JWKS verification, facility-role authorization, append-only audit write helpers, a consolidated index migration, workflow slices for many clinical and administrative domains, schema-focused tests, documentation, and a standalone control-plane HTML prototype.

The following are still absent or unverified: production frontend/PWA, full tenant/facility/purpose ABAC, externally enforced audit immutability, production secret-manager integration, a complete ordered migration framework, real replica-set integration tests, end-to-end workflows, complete inventory and financial subledgers, comprehensive medication/clinical decision safety, actual offline clients and conflict application, FHIR/national adapters, operational workers/outbox, production infrastructure, monitoring, backups/restores, disaster recovery, and formal country/facility approvals.

A green CI run is necessary but not sufficient for any production release.

## 3. Remediations implemented in this re-audit

### R-01 — Database schema migration readiness gate

**Finding:** The previous readiness endpoint could report ready after MongoDB ping and OIDC JWKS checks even when the index migration had never run.

**Change:** Added baseline schema version 2026.11.27.1. The index migration records this marker only after every index operation completes. The readiness endpoint now checks MongoDB, the applied baseline marker and OIDC JWKS, and returns a specific schema_migrations_pending failure when the marker is absent.

**Files:** apps/api/src/odei_api/main.py, apps/api/src/odei_api/migrations/control_plane_indexes.py, apps/api/src/odei_api/migrate.py.

**Tests:** Added a parameterized health test for both pending and applied schema marker cases in apps/api/tests/test_health.py.

**Boundary:** This is an initial baseline ledger marker, not a mature migration framework. Ordered immutable migrations, checksums, migration locking, rollback/forward-recovery policy, schema drift detection and real database upgrade tests remain outstanding. Readiness still does not validate production secret manager, object storage, workers/outbox, telemetry or downstream integrations.

Removed a stale sentence implying that already implemented API foundations were still future M1 tasks. Rewrote the readiness description to identify its exact current dependency checks and explicitly state that a ready response is not production release approval. Added a link to this re-audit.

## 6. Highest-priority open defects and release blockers

### P0 — No production clinical or financial release

No independent security assessment, clinical safety case, facility acceptance, regulatory/jurisdictional approval, staff training evidence, production data protection controls or disaster-recovery exercise is present. Keep live use disabled.

### P0 — Main branch is not protected

The repository reports main as unprotected and no required status checks. This permits direct pushes without required review or CI enforcement. Configure a GitHub ruleset/branch protection outside this code change: require pull requests, at least one independent review, required repository-check status, stale-review dismissal, conversation resolution and restricted force-push/deletion. Confirm the rule is active after configuration.

### P0 — Audit immutability is not enforced

The application helper only appends events. Configure a dedicated MongoDB audit role with insert/find and explicit update/delete denial; test denial against the real target database. Add tamper-evident export/retention and audit privileged reads.

### P0 — Clinical safety and authorization are not independently validated

Clinical write routes have role checks, but this does not establish professional licensing, credential validity, care relationship, consent, purpose limitation, patient-specific restrictions or specialty privilege. Implement policy enforcement and independent clinical safety review before use.

### P1 — Tenant and facility isolation evidence is incomplete

Add an exhaustive endpoint/resource authorization matrix, including nested identifiers and cross-tenant/cross-facility references. Test every read and write route against authorized, unauthorized, suspended, revoked, expired and wrong-facility identities.

### P1 — Financial and inventory ledgers are incomplete

Every stock change must be traceable through one stock ledger, and financial subledgers must reconcile to balanced GL journals. Add reversals, reconciliation, concurrency and close-period tests.

### P1 — Integration and concurrency tests are insufficient

Use disposable MongoDB replica-set integration environments. Test transaction rollback, duplicate races, retry/idempotency, stale writes, simultaneous stock dispense, cash-session close/payment, bed allocation, role revocation and audit failure.

### P1 — Production operations and integrations are absent

Build and verify the production UI, deployment topology, secrets adapter, durable workers/outbox, telemetry, encrypted backup/restore, disaster recovery, monitoring, FHIR/national interfaces and provider-specific adapters.

### P1 — Uganda country profile is draft

The Uganda profile must be reviewed and approved by local legal/privacy, clinical, finance, security and operations owners. Evidence applicable data-controller/processor registration, notices, lawful bases, retention, breach handling, cross-border transfer assessment and national reporting obligations before live personal data processing.

## 12. Cash-session operator identity scope correction

A source-level review of finance routes found that opening and closing cash-session ownership checks keyed the operator by OIDC `subject` alone, while payment receipt already checked both issuer and subject. OIDC subjects are issuer-scoped identifiers; two identity providers can legitimately issue the same subject string. The old query could therefore block one operator because another issuer used the same subject, and could allow a different issuer to close a session if it knew the session identifier.

The finance routes now include both `opening_by_issuer` and `opening_by_subject` in the open-session duplicate check, payment ownership check, and close-session ownership check. The migration replaces incompatible prior indexes with issuer+subject compound indexes using the same persisted field names. A subsequent field-name mismatch was identified and corrected in section 13.

This is a code-level correction only. The index replacement path needs a real MongoDB migration test, especially where pre-existing duplicate open sessions exist. The change must pass CI before being considered verified.


## 13. Cash-session identity field consistency

A follow-up review found a field-name mismatch introduced while issuer-qualifying cash-session ownership: the session writer persisted `opening_by_subject`, while the ownership helper and compound indexes expected `opening_by_subject`. This prevented an operator from finding their own open drawer and could make the unique compound index collide for unrelated operators in the same facility. The helper, index definitions, and regression expectation now use the persisted `opening_by_subject` field consistently. CI and a MongoDB replica-set migration/integration test remain required before deployment.
